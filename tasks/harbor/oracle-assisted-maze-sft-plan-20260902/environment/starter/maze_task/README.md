# Oracle-assisted maze SFT

Edit `maze_task/candidate.py`. Its `build_examples(train_groups)` function receives grouped training mazes and returns `(catalog_id, weight, is_negative)` selections from each group's `catalog`. Records expose their ID, kind, complete-grid state, action, and permitted treatment. Kinds are `canonical`, `alternative`, `correct_prefix`, `recovery`, and `failure_error`. Positive records use `-log(p(action))`; `failure_error` records use `-log(1-p(action))`. IDs bind examples to the supplied training groups. Changing a record's permitted treatment is rejected.

Keep the implementation self-contained in `candidate.py`. The evaluator copies only that source file into the construction worker; other submission files are not added to its import path. These limits apply to each construction call, across all supplied training groups:

- Return a nonempty list or tuple with at most 70,000 selections. Repeated IDs count toward this limit.
- Weights must be finite, nonnegative numbers. They are stored as float32 and must remain finite, with a positive total weight.
- The candidate source and the worker's JSON selection output must each be regular files of at most 8,000,000 bytes. The worker serializes the returned selections; the candidate does not need to write this output file.
- Reconstructed training arrays must use at most 430,000,000 bytes.
- The construction worker has a 300-second CPU-time limit and a 900-second wall-clock limit. These include worker startup, input loading, candidate import, and output serialization. It starts with one PyTorch CPU thread and CUDA devices hidden. GPU training runs separately in evaluator-owned workers.

Recovery actions respect walls and visited cells and lead along a shortest remaining route without a revisit. A failure state with no remaining route supplies no recovery, correct-prefix, or failure-error labels.

Use `public_test.sh --mode contract` for a CPU-only check on four training mazes. It checks the same selection contract but does not measure quality. Use `--mode quick` only as a training smoke test: 48 training mazes, 24 evaluation mazes, 120 updates, and batch size 32 per run. Quick mode keeps one run per panel with seeds 17, 29, and 43. Use `--mode full` for comparisons: 192 training mazes, 96 evaluation mazes, 600 updates, and batch size 64 per run. Full mode uses three disjoint panels with seed pairs (17, 101), (29, 101), and (43, 101). These are six runs per method, not six distinct panels. Each run starts from the same fixed model checkpoint. The score uses the final training step; validation NLL is only a diagnostic.

Only `public_test.sh --mode full` creates an automatic checkpoint. It first saves the submission with `checkpoint.sh`, then restores and tests that saved copy. Later workspace edits do not change the tested code. Contract, quick (including the default mode), and help requests do not create saves. Concurrent saves wait for a per-sandbox lock; restores and tests can run in parallel. A save or restore failure stops the full test. Failed full tests keep their input checkpoint. Checkpoint messages go to stderr so stdout remains the test result. Saves go to `/logs/artifacts/progress` for later offline waypoint grading; no private grading runs inside this script. After any final edits, run another full test or use `checkpoint.sh --label final`.

For full tests, the script also keeps records under `/logs/artifacts/public-tests/<checkpoint-id>/`: `checkpoint.txt` contains the checkpoint metadata and snapshot digest; `arguments.txt` lists the test arguments; `result.json` contains stdout; `stderr.log` contains stderr; and `exit-code.txt` contains the test exit code. An exit code of zero marks a completed, successful test. A nonzero code marks a failed test. A missing exit-code file means the test did not finish normally; do not treat partial output as a score. Only completed, successful full tests supply public scores for checkpoint comparisons.

Data version `expanded-panels-v2` has six disjoint public panels, each with 192 training and 96 evaluation mazes. Full mode uses panels 0–2 by default. Use `--mode full --validation-fold 1` for panels 3–5. These are two disjoint validation sets, not overlapping cross-validation folds. No evaluation maze enters any training panel. Repeated tuning can still overfit public data. The command prints its result as JSON; it does not cache scores.

The official verifier uses six private panels: 1,152 training and 576 evaluation mazes in total. Seed pairs (17, 101), (29, 101), and (43, 101) repeat across these panels, giving twelve runs per method. Baseline and candidate use the same data and training-order seed in each pair. Full public and private rewards are the candidate's mean path quality across all runs (six publicly, twelve privately), between 0 and 1. Every evaluation maze counts under both seeds, including failures. For a successful path of length L, quality is `clamp((60-L)/(60-L*),0,1)`, where L* is the shortest path length. Incomplete paths receive zero. A reward of 1 requires shortest-path solutions on every evaluation maze in every run. Reports retain the baseline mean quality and candidate/baseline ratio as diagnostics; the ratio is not the reward. A candidate that matches the baseline receives its mean quality, not a reward of 1. Decoding masks walls and revisits; the model must learn which legal branch reaches the goal. This measures example selection and weighting, not training speed or unassisted move legality.

Candidate code runs in a resource-bounded subprocess within the separate verifier sandbox. The parent validates returned IDs, weights, and treatments and reconstructs training states and labels from its own catalog. It does not accept candidate-supplied labels or scores. This subprocess is not an OS security boundary: it shares the verifier's filesystem and user permissions. Candidate code must use only the supplied training groups and must not read private fixtures or modify evaluator files.

All scored mazes come from reproducible full-source samples of the pinned `max-rl/maze_17x17_diverse_1.3m` dataset and exclude old fixture mazes by ID and exact grid. Evaluation version `quality-v1` uses the same data and schedules as private `mean-v5` and public `mean-v4`, but returns candidate mean quality instead of the candidate/baseline ratio. Quick mode uses this reward scale too; it remains only a smoke test. The model, optimizer, per-run budget, per-path quality, and contract check are unchanged. Do not compare the new 0–1 rewards directly with historical ratio rewards.
